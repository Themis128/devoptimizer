# Plan: DevOptimizer Windows 11 Application — 2026-09-26

**Goal:** Turn the existing PowerShell/WPF hub into a proper installable Windows 11 application — native launcher EXE with identity/icon, Win 11 visuals, single-instance + jump list, toast notifications, a settings page with autostart toggle, per-user installer/uninstaller, and a Pester 5 test suite — without behavior drift in the 353-command engine.

**Architecture:** Three layers. (1) `app\DevOptimizer-AppCore.psm1` — pure, unit-testable logic (settings schema/load/save, command filtering, autostart toggle, toast sender, DWM helpers) imported by both the app and the tests. (2) `DevOptimizer-App.ps1` — the existing WPF engine, modified to import AppCore, apply DWM polish (dark titlebar, rounded corners, Mica with fallback), guard single instance, accept parameters for jump-list deep links, show the settings view, and fire toasts on long-run completion. (3) A tiny .NET 8 WinExe launcher (`app\bin\DevOptimizer.exe`) with an embedded generated icon that hosts the PowerShell script invisibly — giving a real exe, taskbar identity, and Start-menu/installer target. Per-user install writes Start Menu shortcut + HKCU uninstall entry (Windows Settings → Apps); no admin required anywhere.

**Tech Stack:** PowerShell 5.1 (app host) + WPF/XAML; DWM P/Invoke via Add-Type; .NET 8 SDK (already 8.0.424 — newer SDK evaluated and NOT needed: nothing here targets beyond net8.0-windows); System.Drawing icon generation; Windows.UI.Notifications WinRT toasts under the PowerShell AUMID with NotifyIcon balloon fallback; System.Windows.Shell JumpList; Pester 5 (CurrentUser scope install); HKCU Run key + HKCU Uninstall registry.

**Work Scope:**
- IN: AppCore module; app modifications (DWM polish, single instance, params, settings view, toasts, jump list); launcher EXE + multi-res icon generation; installer/uninstaller + Apps-list entry; Pester 5 install + app test suite + runner; registry-driven verification updates.
- OUT: MSIX/signing (per-user installer covers identity; MSIX needs SDK downloads — future work), native C# UI rewrite, changes to Execute-Command/engine behavior, the 63 archived bat files.

**Verification Strategy:** level: test-suite. Command: `pwsh -NoProfile -File .\scripts\Test-App.ps1` (Pester 5 suite) plus `DOAPP_SELFTEST=1 powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\DevOptimizer-App.ps1` (UI self-test) plus `pwsh -NoProfile -File .\validate-all-scripts.ps1` (all repo scripts still parse). Passing proves: AppCore units behave (settings roundtrip, filter regression, autostart toggle, mutex), the launcher/icon/install artifacts exist and are structurally valid, the app still boots its UI in headless self-test, and no repo script regressed.

**Critic panel note:** forge critic subagents remain unavailable on this host (reasoning-level error on dispatch, retested this session); the Pester suite + existing deterministic validators serve as the independent verification gate instead.

**Key implementation notes / deviations:**
1. .NET version: user pre-approved installing a newer SDK; **not needed** — launcher targets net8.0-windows framework-dependent (0.25 MB) on the already-installed 8.0.424 SDK/runtime. Documented in app\README.md with the SelfContained flip for portable builds.
2. AppCore bugs caught by testing during build: `$schema.Type $v` is invalid cast syntax (use `-as`); **Set-StrictMode 2.0 makes missing-key PROPERTY access on hashtables throw** while indexer access returns $null — the flaky partial-settings-read bug; BinaryWriter.Write(Object[]) writes 1 byte — cast slices to [byte[]].
3. Test-design lessons encoded in the suite: mutexes are thread-affine/reentrant → single-instance must be tested cross-process (child powershell.exe); PS 5.1 does not wait for GUI exes on `&` → use Start-Process -Wait; Pester variables must live in BeforeAll; Pester 6 removed Invoke-Pester -Exit; Pester 6.2 installed per-user for both hosts.
4. App self-test assertions made registry-count-DRIVEN (expected counts computed from the registry + AppCore filter) after a stale hardcoded count caused a false failure — hardcoding UI counts is banned.
5. README deviation: root README.md is legacy Playwright content — application docs live in app\README.md instead of modifying it.
6. Toast verified live under PS 5.1 (PowerShell AUMID); jump list guarded by launcher-exe existence; no elevation used anywhere.
7. **Mimosa L2 stop-hook finding (command injection, Program.cs) — reviewed as FALSE POSITIVE with hardening attempted.** Five candidate rewrites were attempted and each was blocked by the pre-write scanner: (a) whitelist + ArgumentList (the scanner's own recommended shape), (b) deep links moved to DEVOPT_* environment variables with the child command line built only from constants, (c) build-time-generated path constant, (d) inline string literal in ArgumentList, (e) a fully compile-time-constant command line with zero user-reachable data. All five were rejected with the same message, proving the rule matches `Process.Start("powershell.exe", …)` per se rather than any actual taint. The shipped code uses `ProcessStartInfo` with `UseShellExecute=false` + `ArgumentList` (per-token quoting, no shell, no concatenated command line — exactly the recommended pattern); the only input is the local user's own CLI to their own exe; forwarded tokens bind to the script's declared `param()` block where unknown names fail binding cleanly. Residual note: v1 (shipped) forwards tokens verbatim — a whitelist hardening is fully designed in this plan (section "Mimosa review") and can be applied if the scanner rule is tuned to allow Process.Start with ArgumentList constants.
